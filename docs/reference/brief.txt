1. Product goal

Local Chat lets people on the same local network share text, links, and code snippets in named rooms.

The intended users are ordinary people, not network engineers. The expected group size is 2–20 computers.

The normal experience must be:

1. Install the application.
2. Open it.
3. Allow local-network access if the operating system asks.
4. Automatically see other running copies and the available rooms.
5. Read, send, and copy information.

Users must not need accounts, joining codes, IP addresses, DNS settings, a terminal, or a separately installed server.

All rooms on the current network are visible to everyone using the app there. Everyone can read and send messages in those rooms.

Internet access is not required for local communication.

8. Interaction and motion rules

Every animation needs a functional reason.

Use motion to confirm an action, explain a small state change, or soften an occasional overlay transition.

Recommended behavior:

- Copy: immediately change the icon or label to a checkmark confirmation, then restore it after approximately 1.5 seconds.
- Buttons: subtle press feedback.
- Pointer-opened menus: a short fade or very small movement from the trigger.
- Occasional dialogs and panels: restrained, interruptible transitions.
- Connection changes: update text and status calmly without repeatedly distracting the user.

Keep most transitions around 100–180 ms. Occasional overlays may use up to approximately 220 ms if that feels better in testing.

Room switching, typing, keyboard shortcuts, and search results must feel immediate.

Animate transform and opacity where practical. Avoid expensive blur, animated layout dimensions, continuous decorative effects, and broad "transition: all" rules.

Respect reduced-motion preferences. Preserve clear feedback when movement is disabled.

11. Networking design

Use discovery to find peers, then communicate over reliable encrypted connections.

Do not broadcast every chat message as a UDP datagram.

Initial topology:
- Each device discovers other running copies.
- Each device connects directly to available peers.
- There is no permanent central server.
- At 20 computers, each device needs at most 19 peer connections.

This avoids making one user's laptop responsible for keeping the whole conversation running.

Before implementation, briefly compare this with an elected-coordinator approach and record the decision. Prefer the direct-peer approach unless a prototype demonstrates a concrete problem.

Discovery:
- Use mDNS/DNS-SD.
- Advertise a dedicated service such as _localchat._tcp.local.
- Include a protocol identifier, compatible version, peer identifier, and listening endpoint.
- Keep messages and room contents out of discovery records.
- Handle duplicate announcements and changing addresses.
- Bind discovery and connections to the intended local network interface.
- Keep VPN and virtual interfaces from accidentally extending the sharing boundary.

Connections:
- Use a versioned protocol over TLS.
- Use bounded length-prefixed frames or another well-defined framing scheme.
- Set connection timeouts, frame limits, and bounded queues.
- Apply backpressure when a peer is slow.
- Resolve simultaneous connection attempts deterministically.
- Reconnect with backoff and jitter.
- Re-establish discovery and sessions after sleep or interface changes.

Use maintained cryptographic libraries. Do not invent encryption.

Bind peer identity to a persistent installation key. Document first-contact trust honestly: automatic discovery establishes a device identity, not proof of a person's real-world identity.

Do not implement certificate verification as "accept everything".

12. Network changes and previous history

This is a required behavior, not a later enhancement.

A laptop moving to another network must not automatically offer its previous network's rooms and history to the people there.

Separate these concepts:

- Device identity.
- Current network context.
- Shared room namespace.
- Locally retained history.
- History currently eligible for synchronization.

Every database query and synchronization operation must respect that separation.

Required behavior:

- On a recognized current network, synchronize eligible history with current peers.
- On a new network, discover the people and current rooms there automatically.
- Keep old history available locally in a Previous networks area.
- Do not include old history in advertisements, room catalogs, synchronization responses, or pending-message delivery on the new network.
- Pause existing exports and connections while reevaluating a network change.
- Never use recognition of a familiar peer alone as permission to export old history.

Network identity needs an early technical prototype.

A Wi-Fi name, IP range, or device list alone is not a reliable unique network identifier. Different networks can share those values.

Use conservative combinations of available OS network-context information. Avoid requesting unrelated permissions just to obtain a nicer network label.

When continuity is uncertain:
- Keep old history local and read-only.
- Allow fresh communication with current peers.
- Do not guess that old history is safe to share.

Document the limits of automatic network recognition. Open, unauthenticated LAN discovery cannot provide an absolute guarantee against a network deliberately impersonating another network.

Test at least:
- Disconnect and reconnect to the same network.
- Move between two different networks.
- Two networks with the same SSID or address range.
- Multiple familiar devices moving together.
- Ethernet and Wi-Fi being active simultaneously.
- VPN activation.
- All peers closing and later reopening.
- Separate groups starting simultaneously and subsequently discovering each other.

Resolve this model before enabling historical synchronization. Do not treat a hash of an SSID as a completed solution.

13. Persistence, synchronization, and ownership

Use SQLite as the durable source of truth.

Core records should cover:

- Local installation identity.
- Peer identities and display profiles.
- Network-context mappings.
- Rooms and ownership.
- Immutable message and room-management events.
- Synchronization progress.
- Pending delivery.
- Local drafts.
- Local read positions, mute settings, and preferences.

Give each room and event a stable identifier. Names are labels, not identifiers.

For each event, define:
- Protocol/schema version.
- Shared context or namespace.
- Event identifier.
- Author identity.
- Author sequence.
- Logical ordering value.
- Display timestamp.
- Event type and payload.
- Signature.

Use deterministic encoding for signed data.

Do not depend solely on wall-clock timestamps for ordering. Computers can have incorrect clocks.

Message flow:
1. Validate the command.
2. Persist the event and pending-delivery state transactionally.
3. Show the message immediately.
4. Send it to connected peers.
5. A receiving peer validates and persists it.
6. Acknowledge durable receipt.
7. Update delivery state.

Retries must not create duplicate messages.

Delivery labels must distinguish:
- Saved locally or waiting for peers.
- Shared with connected peers.
- A failure requiring attention.

An acknowledgement is not a read receipt. Do not label a message "read" just because another computer stored it.

Synchronization:
- Exchange compact summaries.
- Request missing events in bounded batches.
- Track missing ranges, not just the largest sequence number observed.
- Resume interrupted synchronization.
- Allow a returning device to recover history from any eligible peer retaining it.
- Allow peers to relay valid historical events without the original author being online.
- Avoid repeatedly transferring the complete history.

Room management:
- Verify creator authority in Rust and on receiving peers.
- Hiding a menu item is not authorization.
- Preserve signatures so relayed room changes can be verified.
- Define deterministic ordering for rename/archive/restore events.
- Keep messages sent before a device learned about an archive; do not silently discard them.

In version one, "creator" means the installation identity that created the room. A matching display name on another computer does not grant ownership.

If an identity key is lost, do not silently transfer its ownership rights.

14. Content handling and practical limits

Start with explicit limits, for example:

- Room name: 80 characters.
- Room description: 240 characters.
- Message content: 64 KiB of UTF-8.
- Bounded synchronization batches and network frames.

Keep these limits centralized and documented.

Render messages as text or a constrained safe format. Never execute received HTML, scripts, or code.

Code snippets are for reading and copying, not execution.

For version one, links can display their URL and hostname. Avoid automatically fetching previews from arbitrary URLs.

Use parameterized database queries and safely constructed search queries.

Keep private keys out of frontend state and logs. Use OS credential storage through platform adapters where available.

Do not log message bodies by default.

15. Performance requirements

Treat these as initial engineering targets to measure on the available Mac, not as claims already achieved:

- Warm launch to usable window: approximately 1.5 seconds or less.
- Cached room switching: under 100 ms.
- Local search: under 150 ms at the 95th percentile with 100,000 stored messages.
- Typical idle CPU: below 1% averaged over a measured idle period.
- Aim for approximately 200 MB or less for the application and attributable webview processes in a representative steady state.

Record hardware, OS, release build, dataset, peer load, and measurement method.

If a target is missed, identify the cause and report actual measurements. Do not hide misses or claim a framework automatically guarantees low memory use.

Implementation rules:
- Load messages in pages.
- Keep rendered history bounded.
- Use windowing when needed and verify selection, copying, and scroll anchoring still work.
- Do not load the entire database into frontend memory.
- Keep database work and synchronization off the UI thread.
- Bound caches and outbound queues.
- Avoid a timer per message.
- Stop unnecessary UI work when hidden.
- Avoid re-rendering the whole conversation for a presence change.
- Test long code blocks and bursty catch-up.

Measure production builds. Development tooling is not a representative performance baseline.
